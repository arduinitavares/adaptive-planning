## Intent and agreed behavior

Adaptive planning becomes one persistent service in a Linux container on the user's Mac. Local Codex, Antigravity, and GitHub Copilot sessions connect to the same service. The service preserves plans and recorded execution state so an existing or new orchestrator session can resume work.

The orchestrator remains a capable model running in the user's chosen client. It selects work, assigns agents, requests independent review, accepts results, and revises the plan. The service records and validates those decisions. It does not dispatch agents or continue scheduling after the orchestrator session ends.

Adaptive planning remains independent of the working method. Agents may follow Superpowers for coding, a debugging process, or another suitable workflow. Adaptive-planning instructions require a published checkpoint after each named step and its verification. The service displays the plan and checkpoints, including workflow information that an agent supplies.

Success means sessions can resume the same plan, coordinate concurrent assignments, and use a persistent live dashboard without starting a server per task or using ASCII as the default presentation.

## Planning principle

The inspiration is reinforcement learning: an action changes the situation, so the next decision must use what actually happened. The practical method is closed-loop, receding-horizon planning: build a provisional plan, execute a meaningful step, verify its result and update known facts, then reassess the remaining plan before continuing. The service preserves this feedback loop; storing a checklist alone is insufficient. It does not train a policy or calculate rewards.

The goal stays stable within the user's authorization. The route remains provisional. Evidence determines the next step. Independent bounded steps may run concurrently when their assumptions and resources permit it. Each outcome still feeds back into the shared plan: affected work is held or revised before it advances, and already running affected workers are told to pause at a safe boundary. Unaffected work can continue. There is no promise that the service can interrupt a host-side action already in flight.

## Scope

The first release includes durable plans, explicit orchestrator assignments, concurrent-update protection, task outcomes, evidence, review records, reassessment, a shared dashboard, a Linux container deployment, and connection instructions for the three clients.

It excludes autonomous scheduling, worker self-selection, agent launching, automatic Git integration, remote access, multi-user permissions, model routing, and automatic observation of client conversations. Already dispatched agents follow the lifetime and permissions of their client; the service does not promise to keep them running.

Only published planning and execution state is retained. Conversation transcripts and hidden model reasoning are outside the record. No implementation, installation, deployment, client configuration changes, or Git commit is performed by approving the conversational concept.

## Approach and alternatives

Use a Python application with the official MCP Python SDK, Streamable HTTP, a single SQLite database, and the existing dashboard assets. Keep validation rules from the current publisher as domain behavior; replace per-task serving with one service that routes by durable plan identity.

SQLite supplies one transaction boundary for plans, assignments, and shared-resource reservations. This matters when two different plans use the same workspace or external resource. The deployment uses one service instance and one named data volume. Exact SDK, interpreter, and image versions must be pinned in the implementation plan and checked against the installed clients; protocol compatibility is established by interoperability tests.

Alternatives considered:

1. An MCP facade over separate JSON state directories preserves more storage code, but cross-plan resource reservations would require an additional transactional authority.
2. The recommended shared service keeps storage and coordination under one authority while reusing graph, evidence, and execution-scope rules.
3. A persistent agent orchestration engine adds dispatch, credentials, host execution, scheduling, and recovery responsibilities beyond the agreed service.

## Components and deployment

- **Domain rules:** validate plan graphs, state transitions, evidence, execution scope, checkpoints, and assignments without transport-specific logic.
- **Store:** persist current snapshots and append-only events; perform atomic assignments, compare-and-swap updates, and idempotent retries.
- **MCP interface:** expose plan queries and semantic mutations. Clients do not submit filesystem paths for the container to read or write.
- **Dashboard:** render plans, dependencies, owners, checkpoints, evidence, reviews, and published activity from the same store.
- **Agent instructions:** specify when to publish, how to resume, how to handle conflicts, and how to report unavailable service state.

The service listens on the container network interface. Docker publishes its fixed configured port only on the Mac's `127.0.0.1`. The MCP endpoint is `/mcp`; `/` lists plans and `/plans/<planId>` is a stable plan view. Every mutation returns the plan ID, current generation/revision, and dashboard URL.

Use a non-root container, a dedicated named volume, and `unless-stopped` restart policy. Closing a client session does not stop the container. Availability still depends on the Mac and Docker runtime running; sleep, shutdown, or a manually stopped container does not imply continuous availability.

Do not mount the host Docker socket, repositories, home directory, or client credentials into the container. The service does not edit working trees or execute project commands. Container removal must preserve the data volume; installation and update instructions must not remove it implicitly.

All MCP requests require a shared, per-installation bearer credential kept out of URLs and logs. Client-specific setup supplies it through supported configuration mechanisms. The read-only dashboard is available on loopback under the single-local-user trust boundary, with strict Host/Origin handling, no permissive cross-origin access, escaped content, and a restrictive content security policy. It has no mutation controls in this release. Actor labels are attribution, not authenticated identities or proof of human authorization. Derive allowed loopback Host/Origin values from the validated public base URL and its bound port; the production default remains 8790. Ephemeral integration tests configure their actual listener port rather than broadening the allowlist.

## Plan and artifact identity

A service-generated `planId` identifies the durable plan. Its objective, acceptance criteria, constraints, recorded authorization, repository/workspace references, optional workflow name/phase, steps, and artifact references survive client disconnection.

Each step retains a stable `stepId`, title, dependencies, completion check, evidence, and status. Completed and retired work remains in history. An agent-supplied phase label such as `brainstorming` or `implementation` is optional metadata; there is no required Superpowers sequence.

Create requests carry a caller-generated durable creation ID as well as an idempotency key. That creation ID maps to one plan even if a retry accidentally changes its request key. A fresh session first lists open plans; a matching objective/workspace is reported as a possible duplicate, never silently merged. A deliberately separate plan records explicit new-plan intent.

Retain the default horizon of at most ten upcoming steps unless the user specifies another horizon. Retain the current snapshot limits of 200 total nodes, 50 evidence items per step, and 10 MB per public projection/page; report content limit violations without truncating evidence. The durable event record retains published checkpoints and rulings across the bounded snapshot history. Coordination is a summary and bounded page, with current/unresolved work prioritized and complete records reachable through revision-bound pagination. Historical attempts/reviews do not accumulate inside one materialized snapshot. Cursors bind the installation epoch, target plan revision and a store-wide committed event-sequence watermark read in the same SQLite snapshot. Changes made by another plan to shared orphan uses invalidate the cursor even without changing the target plan revision. Clients discard partial pages and reread on conflict or any changed component. This watermark does not add another authorization or compare-and-swap revision. Resource release and hold resolution cannot fail merely because historical coordination grew; their evidence/reasons remain in the event ledger and resolved records leave the current page. Archiving or deleting authoritative records is an explicit maintenance action.

Keep `generation` as a UUID identifying a storage epoch and `revision` as a monotonic update counter. Ordinary changes advance revision, not generation. Recovery that replaces an epoch changes generation and invalidates stale operations. These concepts must not be conflated with workflow phases or numbered tasks.

The MCP store is authoritative for the current graph, ownership, recorded outcomes, and progress. Design documents and implementation plans hold their detailed instructions. They are referenced by path, branch/commit identity, and document version; task IDs connect their instructions to the shared graph. An orchestrator publishes any changed task definitions explicitly, preserving the reference to the document version that justified the change. The dashboard and local execution notes are views or working records, not independent authoritative progress trackers.

The service cannot open Mac-side document paths. Agents use their normal repository tools to read referenced documents. Checkpoints must preserve a useful handoff summary and evidence before temporary workflow artifacts are cleaned up. Essential evidence text and review findings belong in the durable record; a temporary-file link alone is insufficient.

## Plan, step, and assignment states

Retain the existing plan states: `planning`, `running`, `stopped`, `blocked`, and `complete`. Retain step states: `pending`, `in-progress`, `blocked`, `complete`, and `retired`.

Assignment attempts are separate records with an assignee label, random attempt token, declared workspace/resource keys, definition version, last activity, and outcome. Their lifecycle distinguishes assigned, active, submitted, accepted, rejected, released, and stale work. Submitted work remains an incomplete plan step until its required verification and review have been accepted. Staleness preserves the previous attempt state for explicit recovery.

| Event or condition | Attempt and step state | Reservation behavior |
| --- | --- | --- |
| Assign | Attempt `assigned`; step `pending` and unavailable to another implementation attempt | Acquire declared resources atomically. |
| Start | Attempt `active`; step `in-progress` | Keep reservations. |
| Submit a verified result | Attempt `submitted`; step `in-progress` awaiting acceptance/review | Keep reservations through review and any fixes. |
| Submit failure/blocker, or record a failed review | Attempt remains `submitted`; step `blocked` | Keep its token, definition, latch and reservations for an explicit fix decision. A failed review does not fence the worker. |
| Reopen for an authorized fix or artifact supersession | Explicit orchestrator operation changes `submitted` to `active`, increments attempt version; step `in-progress` | Same attempt/token/resources; preserve prior checkpoints/reviews. A new artifact needs a new checkpoint and matching review. No terminal, stale or held attempt is reopened. Reacquire implementation write use only after conflicting verification/handoff uses are explicitly stopped/released. |
| Explicitly reject a result | Attempt `rejected`; step `blocked` | Fence its token; keep reservations until prior use is confirmed stopped. |
| Accept | Attempt `accepted`; step `complete` | Release only resources with recorded stopped-use confirmation; otherwise retain an explicit recovery obligation. |
| Cancel/release | Attempt `released`; step becomes explicitly `pending`, `blocked`, or `retired` | Release only confirmed-stopped resources; retain unresolved reservations independently. |
| Stale detection | Attempt `stale`; step retains its prior state with an execution hold | Retain reservations; time alone releases nothing. |

Plan status is a derived view with this precedence: explicit stop is `stopped`; all non-retired steps accepted with final gates passed and no unresolved holds/recovery obligations is `complete`; any live assigned/active/submitted attempt or currently executable step in a started plan is `running`; a started plan with no executable/live work and outstanding blockers, holds, stale ownership, or required remediation is `blocked`; otherwise it is `planning`. A blocked sibling does not make a plan with independent live work globally blocked. Imported explicit stop/block reasons are preserved as controls, not erased by deriving the view.

Assignment readiness is derived from current state: all dependencies accepted complete, step pending, no live or stale unresolved assignment, no unresolved material reassessment affecting the step, recorded execution scope permits the work, and no conflicting reservation. A listed ready step is advisory; the assignment transaction rechecks every condition. Starting an assigned step additionally requires recorded availability of its accepted prerequisite outputs in that worker's execution context.

Every accepted result has a stable result-version ID and its output references: commit/diff identity, document/data digest, or the durable observation checkpoint as appropriate. A consumer attempt binds each prerequisite to that accepted result version. Before start, the orchestrator records the consumer workspace/base identity and how its required outputs were made available and checked. For code, record the prerequisite as an ancestor of the checked base, a merge/cherry-pick with its resulting base and verification evidence, or a supplied equivalent artifact with its digest and check. When multiple prerequisites are integrated, record all result-version bindings against the final checked base. Missing inputs block starting. The service checks bindings and required availability attestations; host-side tools establish availability and preserve their evidence.

The existing `nextStepId` may remain a planning hint for compatibility. It does not limit the dashboard to one active worker. Parallel eligibility follows the dependency graph and reservations.

## Generic checkpoint requirement

Agent instructions require this sequence for every named plan step:

1. Publish or resume the canonical plan before starting work.
2. Have the orchestrator assign the step; mark it started using that assignment.
3. Perform the bounded work and its completion check.
4. Publish the actual result, evidence, failures/blockers, and a reassessment of the remaining plan.
5. Continue only within the recorded and actual user authorization.

The initial plan must identify the objective, acceptance criteria, constraints, execution mode, known facts/assumptions, and concrete next check. A step is a named unit with a checkable outcome; an individual tool call is not automatically a step. Superpowers tasks can supply these units, with RED/GREEN, review rounds, and other substeps recorded as checkpoint details.

A finished-step checkpoint includes the step and attempt IDs, outcome, check performed, evidence, changes to relevant facts/assumptions, reassessment summary, and proposed changes to the remaining graph or an explicit unchanged result with a reason. Failed verification is a failed or blocked outcome, never completion. Reassessment does not authorize a wider scope.

Workers may propose reassessment changes; the current orchestrator classifies material effects and resolves them against the current graph, recording its reason. Acceptance must either apply valid changes transactionally, reject the proposal with an explicit reason, or persist a hold on other affected steps until reconciliation. A proposal identifies affected step IDs; holds cover those steps and their transitive dependents. If its effects are not yet bounded, hold new assignments, starts, and acceptance in that plan until they are assessed. Assigning, starting, or accepting a held step is refused even if its attempt was already active. An unaffected proposer may be accepted while other steps are held. Already accepted history stays intact, but invalidated outputs receive an explicit invalidation record and holds on their consumers until corrective work resolves it. Existing unaffected sibling assignments can continue; the orchestrator relays holds to affected running workers so they pause at a safe boundary. A checkpoint that identifies a missing prerequisite cannot unlock the old graph by merely describing that prerequisite in prose.

A checkpoint proposing changed prerequisites, invalidated assumptions/results, or other material route changes installs provisional holds atomically with publication, before the proposer is reviewed or accepted. The worker names affected steps or declares effects unbounded; unbounded effects provisionally hold the plan. The orchestrator subsequently narrows, resolves, or rejects those holds with an explicit reason. A pending reassessment cannot leave affected work temporarily eligible between submission and acceptance. An explicitly unchanged reassessment with a reason does not itself impose a hold.

The orchestrator can explicitly invalidate a named accepted result from later evidence without rewriting completed history. Record the invalidation, a remediation hold on the producer itself, and transitive consumer holds together. Invalidating a last accepted step with no consumers still prevents plan completion until its own output is revalidated or superseded by accepted corrective work. Resolve each named affected step with passing evidence: revalidate its existing accepted artifact (including required matching review), link an accepted corrective step/result that supersedes the old unusable output, or replan a pending/blocked consumer to valid prerequisites. An active attempt's instructions cannot change through this operation. Supersession links retain both steps and their original result identities; a result belonging to a corrective step is not substituted into another step's result key. For a review-required accepted artifact, revalidation needs a matching passing review recorded after the invalidation. Review recording may append that artifact-bound review while an invalidation is open, without changing completed step or terminal attempt state; a failed review keeps the hold. Resolution evidence names the exact revalidated or corrective artifact/version; generic passing evidence for a different artifact is refused. Other holds remain until individually resolved, and an invalid result remains unavailable to future consumers. Late evidence alone neither accepts work nor clears invalidation.

The service rejects malformed outcomes, evidence-free completion, stale tokens, and changes that violate graph/evidence/scope rules. It requires the recorded checkpoint before accepting that step or allowing dependents to advance. Independent sibling assignments can continue while another worker publishes its checkpoint; there is no blanket wait for all workers to finish.

This enforces recorded progress. The service cannot detect unreported local coding or force a model to call a tool. Compliance comes from the agent instructions and orchestrator supervision. Client hooks are a possible later integration, not a first-release dependency.

## Assignment, concurrency, and review

The orchestrator assigns a step to a chosen worker. Assignment, reservation, and their event are committed together. Two concurrent requests for the same step have exactly one successful outcome. Workers update only their assigned attempt; they do not replace the entire plan or rewrite another worker's tasks.

Each plan has one current orchestrator capability: a random secret token and monotonic ownership version. Creation returns it privately; explicit takeover records the reason, advances ownership version, issues a new token, and fences every prior orchestrator mutation. It does not expire or transfer automatically. The current capability is required for structural edits, assignments, acceptance, review recording/gate changes, hold resolution, resource release, and ownership recovery. Worker attempt tokens allow only that attempt's start, activity, and checkpoint submission. Reads and events expose attribution and ownership versions, never capability secrets. This prevents confused concurrent agents from accidentally exercising another role; the shared installation credential is still a cooperative local trust boundary, not a defense against malicious clients acquiring a takeover capability. Takeover alone neither revokes worker attempts nor releases resources nor renews execution authorization.

Takeover compares the expected ownership version atomically; concurrent requests against the same version have one winner. Resuming a session uses an existing valid capability or explicit takeover, never a new independent orchestrator role. A client may retain its capability in a private local session cache when supported; no cross-session storage feature is assumed. A fresh session without the grant reads the published state and performs an explicit takeover. Capabilities never belong in public documents, events or dashboard URLs.

Capability requirements are normative per operation. Create, import and takeover authenticate the installation/current epoch as bootstrap operations and carry no domain tokens. Direct start/activity/checkpoint commands carry only the assigned attempt token; relayed versions carry both that token and the current orchestrator capability and identify the originating assignee and relay. All other mutations require the current orchestrator capability and carry no worker token. Extra role tokens are rejected, rather than allowing a stale orchestrator token to invalidate a direct worker after takeover. An accepted attempt's token permits only exact replay of its own previously committed worker commands after current epoch/generation validation; it cannot make a new mutation. Explicit rejection, release or replacement fences the old attempt token even for replay.

All mutations have a caller-generated idempotency key, unique across operations within the installation's current storage epoch. Committed request/result records are retained for that epoch's lifetime, including after plan completion. Repeating the same key and payload returns its original committed result together with separately labeled current plan metadata. Reusing a key for a different operation or payload is rejected. Capability checks precede replay; fencing cannot be bypassed by retrying an old key. A changed storage epoch rejects old-epoch requests even when their keys exist in restored history. A lost response cannot create a second assignment or checkpoint. Structural plan edits use generation/revision compare-and-swap and the current orchestrator capability. Task updates check the generation, attempt token, attempt version, and frozen definition version, then merge the semantic update into current state transactionally; another worker's heartbeat does not invalidate an otherwise valid result. Workers propose structural changes in checkpoints; only the orchestrator applies them with the current plan revision. A conflict returns current metadata; the caller rereads and reconciles rather than blindly incrementing revision.

Creation, import that creates a service plan, and takeover are bootstrap exceptions to ordinary capability-before-replay validation: authenticate the installation credential and match the original request identity and payload in the current epoch. Creation/import issue the initial orchestrator grant privately. Their exact retries return the originally issued capability only while that ownership grant remains current. Import deduplication by legacy-source identity follows the same rule even with a different request key. After supersession, return a non-secret committed receipt and current ownership metadata rather than the original secret; acquiring authority requires explicit takeover. All other mutation replays require a currently valid operation-authorizing capability. A stale epoch never receives a capability through replay. This import exception establishes ownership of a new service plan; it does not renew execution authorization or release imported recovery obligations.

The store uses short write transactions covering validation and changes, with bounded contention waits and no model calls, network operations, or project commands inside a transaction. Events and snapshots commit together. Dashboard notifications occur only after commit; reconnecting clients reread committed state.

Every assignment that mutates local files reserves its physical workspace. Shared resources such as a test database need additional explicit reservations. A task that mutates only an external resource reserves that resource without inventing a local workspace. Pure reads of immutable artifacts do not require a writable-workspace reservation; tests that mutate workspaces or shared resources do. Reservations are checked across all plans in the same store. Parallel development normally uses distinct worktrees; the orchestrator must still judge interface and integration risks. Resource declarations are cooperative claims, not filesystem locks.

Use a shared installation `hostId` and registered physical identities. Each assignment declares a repository-scoped, non-repository workspace, external-resource-only, or read-only context. On the Mac, the orchestrator supplies the filesystem identity (device/inode) of the resolved common Git directory when a repository applies and of the resolved working root for a physical workspace, with resolved paths retained for display. A non-Git document/data workspace registers its working root directly. Match a known resource conservatively by either its physical identity or a registered canonical path alias on that host, so device changes or path reuse cannot silently bypass an unresolved reservation. Case-fold path aliases only for a host-attested case-insensitive volume; do not collapse distinct paths on a case-sensitive volume. Conflicting identity/path claims require explicit reconciliation and keep old reservations held. The service returns registry IDs reused by all clients; aliases of the same physical directory reuse its ID. Shared external resources use a registered host/resource identity agreed by the orchestrator. The service cannot discover omitted resources or verify the client's filesystem claims.

Reservation overlap is explicit: a repository-exclusive reservation conflicts with every workspace reservation in that repository; a workspace-exclusive reservation conflicts with another reservation of that physical workspace; an external-resource reservation conflicts with another of the same registered resource. Repository-scoped work with known repository but unknown workspace/write scope reserves the entire repository; missing required repository identity blocks execution assignment. Non-repository work declares that context explicitly and reserves its known physical workspace and external resources. Missing identity for any required writable resource blocks assignment; an explicit non-repository context is different from an unknown repository. This overlap predicate applies to both active and unresolved stale reservations across all plans.

Explicit resource reconciliation records host-attested equivalence and a reason, selects a canonical survivor, and retains durable redirects for prior registry IDs plus every physical/path alias. Conflicting host/kind/case claims or uncertain equivalence are refused. Historical references are not rewritten or deleted. Conflict queries follow redirects, so all old unresolved uses still block the canonical resource. Reconciliation never confirms stopped use, changes liveness, or releases a reservation.

A claimed step's title, completion check, dependencies, and implementation-document version are frozen for that attempt. Changing them requires an explicit orchestrator cancellation/reassignment with the old attempt preserved. A worker cannot submit results against instructions that changed beneath it.

Workers submit attributed evidence: artifact/diff/commit identity, workspace reference, checks and their results, limitations, and blockers. Nonempty evidence is not proof that a check happened. The orchestrator checks evidence and requests the independent review required by the task and user's policy.

Task-specific review requirements gate that task's acceptance. A plan-wide final review is a separate review step dependent on accepted implementation tasks; it gates plan completion and integration readiness, not acceptance of every prerequisite task. This permits inline execution with a final independent branch review without circular dependencies, while retaining per-task review where the chosen workflow requires it. Review records identify the implementation artifact/version, reviewer, verdict, and findings. A code change after review invalidates that review for acceptance. The service can require distinct implementer/reviewer labels and a matching passing verdict, but those labels remain self-declared. It does not certify model independence or execute tests.

Submission and review do not release implementation reservations. A reviewer may inspect an immutable exported artifact without a writable reservation. Reviewer tests or fixes require a reserved execution context: use a separately registered workspace reserved for verification under the same task, or explicitly hand off exclusive use of the held workspace after confirming the implementer stopped using it. Creating or activating writable verification use, including writer handoff, rejects a store-wide execution hold before changing uses or events. Read-only inspection and recording already observed immutable review evidence remain available. An accepted result's invalidation hold alone does not prohibit the artifact-bound review needed for revalidation; ordinary resource conflicts still apply. Record the verification actor and resources before dispatch; no third assignment can acquire them during the handoff. Only one actor may have declared write use of a physical workspace at a time. Review results are relayed by the current orchestrator; the reviewer is not given the implementer's mutation capability. Review/fix handoffs stay within that task's authorized completion checks and never free its first-step latch. A failed final review remains as evidence; retire its unsuccessful review step explicitly, add authorized corrective tasks, and add a new final-review step bound to the corrected branch/artifact and dependent on those tasks. The previous accepted implementation history is preserved.

Acceptance is an explicit current-orchestrator operation. It checks the checkpoint, current attempt, evidence, review requirements, unchanged reviewed artifact, absence of a hold on this step or invalidated prerequisites, and reassessment resolution or recorded holds on other affected work. Acceptance makes the step complete and satisfies the logical prerequisite. Assigning dependents also requires cleared reassessment holds; starting them requires recorded availability of the accepted outputs in their execution contexts. Git integration is performed through the orchestrator's ordinary tools and recorded separately; accepting a step does not claim that its code is merged into a target branch.

## Execution authorization

Preserve `plan-only`, `first-step`, and `complete-task` semantics across all sessions. Record authorization notes as assertions about existing user instructions, not permission grants issued by the server.

Plan-only allows planning, imported historical completions, and blocked/planning state, with no new execution assignment. First-step permits one nonbaseline logical step in its authorization interval across all workers combined. Its existing `scope.claimed` latch remains separate from assignment ownership: releasing, blocking, retiring, disconnecting, or reassigning a worker never frees that latch for a different step. A replacement attempt for that same claimed step remains within the interval; it does not permit a different step. Complete-task still operates within the actual requested objective and constraints.

Resuming a plan, changing clients, importing state, renewing a heartbeat, or changing assignment ownership does not renew authorization. Changes to mode or interval require an authorization note grounded in an actual user instruction. Human workflow approvals and external/destructive-action approvals remain with the user and the client; displaying approval state does not grant it.

## Recovery and unavailable service

Connection/session IDs do not identify plans or own assignments. Reconnecting retains the same attempt only when its current token remains valid. A new orchestrator reads the plan, events, unfinished assignments, blockers, evidence, and open review findings before dispatching work.

When a dispatched worker lacks MCP access, the orchestrator relays its start, observed activity, checkpoints, and review report through its current capability and that assignment's token, identifying both the originating worker and the relay. A relay must preserve the supplied result/evidence and cannot invent verification or liveness. Uninterrupted long tool calls and Mac sleep can produce stale activity; stale means unconfirmed ownership, not proof of failure. A stale but unfenced/unreplaced attempt may publish a checkpoint flagged for recovery, without clearing its hold, changing ownership, being accepted, or releasing resources. Fenced attempts may contribute append-only late evidence/stop reports through the current orchestrator; those notes cannot change executable state or count as an accepted checkpoint until reconciled.

Assignments include activity timestamps and configurable stale detection, defaulting to a 15-minute inactivity threshold. Instructions require workers or their orchestrator relay to report start, checkpoints, and observable activity at least every five minutes when tool access permits; inability to report is handled as unconfirmed ownership, without fabricating a heartbeat. Lack of a heartbeat marks ownership stale and keeps its resource reservations held; time passing never makes it available to another worker automatically. Reads, including dashboard polling, have no side effects. Only an explicit authenticated orchestrator sweep persists stale transitions: one event lists the newly stale attempts and one plan revision advances for the changed batch, while each affected attempt increments its semantic version and preserves prior state/token/resources. An unchanged sweep is a no-op apart from its request receipt; reads may additionally display an overdue warning. Progress operations also reject elapsed inactivity with a structured stale error, so an unswept heartbeat cannot reset the clock or revive ownership. The orchestrator sweeps on resume and before dispatch/recovery, then confirms ownership or records an unfenced late recovery checkpoint using the current attempt version. An unrelated failed command never commits a hidden stale write. Observable activity is a semantic update that advances global revision, so orchestrator structural edits refresh their CAS metadata and retry only after bounded reread/reconciliation.

The orchestrator resolves stale work explicitly. Elapsed inactivity applies to assigned, active and submitted attempts; waiting for review does not permit overdue acceptance or reopening without recovery. A returning heartbeat alone does not reactivate a stale attempt; the orchestrator confirms ownership before it can resume. Confirmation records an actual current ownership observation, restores the prior lifecycle state, establishes the activity timestamp and advances the attempt version. It preserves tokens, checkpoints, latch, unrelated holds and resource reservations; only the corresponding stale/recovery hold clears. Replacement issues a new attempt token and fences old API updates. Each old attempt's resource reservations are retained independently until the orchestrator records that prior use stopped or another explicit safety resolution for that resource. An isolated replacement in workspace Y does not release unresolved workspace X. Replacement must declare its own resources and cannot reuse an unresolved shared database or other resource merely because its worktree differs. The service cannot stop the previous worker's filesystem edits or external actions. No automated worktree deletion, reset, or cleanup is part of recovery.

If the service is unavailable, agents report that condition and preserve local evidence as unpublished working material. An already authorized worker may finish its assigned bounded step and verification. New coordinated assignments and dependent steps wait until a checkpoint is committed and ownership is reconciled. Agents do not start a replacement server or silently create another canonical plan. Retry with the same idempotency key; after conflicts, reread and reconcile.

The presentation default is the dashboard link with a concise checkpoint. If the dashboard cannot be reached, use concise prose identifying the last published revision and any unpublished result. ASCII maps are available only on explicit request.

## MCP operations and client integration

Provide read operations for listing plans, reading a plan and recent events, and listing ready/unavailable steps with reasons. Provide semantic write operations for creating/revising/importing a plan, explicitly taking over orchestration, assigning/starting a step, recording a checkpoint, recording a review, accepting a step, reporting activity, and explicitly resolving/releasing an assignment or verification resource use. Transport inputs are validated structured data, not shell commands or arbitrary container filesystem paths.

Every client connects directly to the same local HTTP endpoint. Document Codex's URL entry, Antigravity's `serverUrl` entry, and Copilot's HTTP server configuration for local CLI/VS Code. Do not claim cloud-hosted sessions can reach the Mac's loopback endpoint. Supply framework-neutral adaptive-planning instructions usable through each client's instruction/skill support. No upstream Superpowers patches are required.

Agents following Superpowers publish generic events and document references through those instructions. Other workflows publish the same structure with their own steps. The service neither invokes skills nor selects models. Delegation, permissions, review-model policy, and worktree management stay in the orchestrator/client.

Retain the legacy publisher/serve path during the transition for tasks that have not been transferred, but make the shared service the updated skill's default. Update `SKILL.md` and `references/live-dashboard.md` together: neither may prescribe per-task server launch or default ASCII in service mode. Legacy files are not writable views into the new store. Import is explicit: clients provide validated v2 state content, and the service records its original tuple, evidence, scope/baseline/claimed latch, and provenance. V1 state first goes through the existing explicit v2 migration procedure. Import must not open a fresh execution interval or claim historical evidence was reverified.

Import establishes an authority handoff. Before transfer, the orchestrator records that writers to the obsolete legacy JSON/publisher authority stopped and that participating agents will publish that task through MCP. This handoff is not blanket evidence that host filesystem or external work stopped; execution-resource stop assertions remain separate. Persist a unique legacy-source identity comprising the shared host ID, registered source directory identity, and original task ID, mapped to the service plan ID. Store its imported digest and tuple as comparison metadata, not as part of the unique identity. Reimporting that source with another request key returns the existing mapping when content matches; changed legacy content produces a handoff conflict, not a second plan or an overwrite. Deliberately creating a different plan is an explicit create operation with its own authorization record. The service cannot fence an obsolete local publisher; the handoff instructions and orchestrator verification must make this boundary explicit.

Import can be the first plan in an empty installation. Supply exactly one existing registered source-directory ID or a physical source-directory workspace claim. For a new request, resolve/register that claim using the shared registry rules inside the same import transaction before legacy-source deduplication; exact committed retries follow the existing replay contract. This registers identity, not execution use or stopped-use confirmation. Validation/conflict failure rolls back new registration with the import. Ordinary resource registration retains its orchestrator authority; no unrelated bootstrap plan is required, and no host directory is opened.

Legacy `in-progress` work imports as unresolved recovery work, not as an executable attempt with a newly minted worker token. Preserve the step and global first-step latch. Known execution contexts may carry registered IDs or physical/external resource claims; resolve/register all claims and acquire conservative reservations inside the same import transaction, registering repository identity before its workspace. Any conflict rejects the whole transaction. Missing required writable-resource identity imposes a store-wide hold, because a hold on only the imported plan cannot protect other plans from the unknown worker. An explicit attach-context recovery operation registers and reserves the previously missing context, preserving the unresolved attempt, tokenlessness and latch; it does not declare stopped use or resume ownership. Clear identity holds only when every unknown obligation is covered. Resolve each active imported step and its resources before resuming execution. Planning inspection and evidence preservation remain available.

Imported unresolved work uses the same recovery rules and code path as stale native attempts; import does not introduce a second ownership mechanism. Prefer transferring quiescent legacy tasks when available.

Corrupt legacy input is rejected; it is not repaired silently. Existing corrupt-state recovery remains explicit and preserves the original evidence as required by the legacy contract.

Use versioned database migrations, refuse newer unsupported schemas, and back up the database consistently before a migration. Rollback uses the previous compatible image and its retained data, or a verified pre-migration backup when schemas are incompatible. Normal restart/recreation retains the same volume and plan URLs. Setup includes explicit export/backup and restore instructions; volume deletion is never an ordinary update step.

Every backup restore is an epoch-changing recovery, not a normal restart. Before serving, mint a new installation epoch and new plan generations, invalidate restored orchestrator/worker capabilities, mark all restored non-terminal attempts stale-unresolved, and impose a store-wide execution hold. Report the backup cutoff and that later assignments/reservations may be absent. New assignments, starts, reopening, acceptance and writable verification reservations stay blocked until the orchestrator reconciles host-side activity, including work absent from the backup, and records a store-wide resolution. Unknown running work cannot be treated as stopped merely because no restored record exists. Retain available pre-restore data/export for reconciliation; restoring a backup never silently releases live reservations.

Store-hold resolution is authorized by the current orchestrator of any one plan, which is named in the command with its capability and an explicit inventory-completeness assertion. Planning-only bootstrap remains possible under the hold; execution is refused. Inventory work absent from the backup can carry resource claims as well as existing IDs. Resolve/register those claims atomically and persist running/unknown work as store-level unresolved uses independent of missing plan/attempt foreign keys. Complete known reservations can outlive the global hold and continue blocking every plan until explicit stopped-use release. Absent work without a fuller execution scope reserves each declared resource conservatively: repository identities conflict with every descendant workspace; workspace and external identities retain their normal exclusive overlap. Unidentified work or incomplete inventory keeps the whole-store hold. Resolution of one restored use cannot silently dispose of another absent obligation.

Official backups are explicitly marked as backup artifacts; serving them directly is refused. The restore procedure verifies the copy and changes its marker, epoch, generations and authority state atomically before serving. Private consistent backups retain capability material under restrictive file permissions; public JSON exports redact credentials, capabilities and private request results. Arbitrary copies of a live authority database outside the supported backup procedure cannot be recognized reliably; operations instructions forbid treating those copies as normal restarts.

## Enforcement boundary

| Rule | Service enforcement | Host/orchestrator responsibility |
| --- | --- | --- |
| Ownership and coordination | Capability/version fencing, transactional resource conflicts, holds and state transitions | Declare actual resources; stop or safely isolate host-side work. |
| Verification and review | Required fields, recorded passing verdict, matching artifact version, checkpoint before acceptance | Run checks; assess evidence; dispatch a genuinely independent reviewer when required. |
| Adaptive replanning | Explicit reassessment and resolution/holds before affected advancement | Interpret observations; propose useful revisions; notify affected workers. |
| Authorization | Recorded mode/latch and interval constraints | Ground permission and any scope changes in actual user instructions. |

## Acceptance checks for implementation

1. Codex, Antigravity, and local Copilot each list tools, read the same plan, and commit a visible checkpoint through their installed client. Report the actual negotiated protocol/version and tested client surface.
2. Closing the creator session, restarting the service, and recreating the container with its existing volume preserve plan identity, revisions, assignments, evidence, and dashboard URLs. A fresh client resumes without redispatching accepted work.
3. Concurrent assignment of the same step has one winner. Independent worktrees can hold separate assignments. Conflicting resources across different plans cannot be assigned concurrently.
   Include aliases of the same physical directory and repository-exclusive versus descendant-workspace overlap. A dependent worker cannot start until accepted prerequisite artifacts are recorded as available in its context.
   A non-Git document/data task can reserve its known workspace, and an external-resource-only task can reserve its registered resource without a repository. Each still rejects a conflicting assignment or an unknown required writable resource.
4. Duplicate requests after lost responses return the original result. Stale revisions, epochs, attempt tokens, and changed idempotency payloads fail without partial mutation.
   Direct worker commands survive orchestrator takeover; a relay using the old orchestrator capability is fenced, and a worker capability cannot call any orchestrator-only operation. Creation retries with a new request key and the same creation ID still yield one plan. Concurrent orchestrator takeovers have one winner; old capabilities cannot mutate or replay a cached mutation, and reads/events never expose their secrets.
5. Active task definitions cannot change silently. Old review results cannot accept changed code. Submission alone cannot unblock a dependency requiring acceptance/review. A failed review can be explicitly reopened, fixed, resubmitted and reviewed on the same attempt without freeing reservations, resetting its first-step latch or fencing its token.
    A checkpoint proposing a corrective prerequisite holds affected work until resolution. A final branch-review step can gate plan completion without preventing its own implementation prerequisites from being accepted.
    An already active held sibling cannot be accepted, and its transitive dependents cannot advance. The unaffected proposer can be accepted with holds elsewhere. A failed final review preserves findings and requires corrective tasks plus a new artifact-bound review.
    Publishing a material reassessment installs provisional holds in that same transaction; affected work cannot advance while the proposer awaits review or acceptance.
6. Checkpoints preserve evidence, record failed verification accurately, and carry an explicit reassessment. Independent workers' updates survive interleaving and become visible in the dashboard.
7. Plan-only and global first-step boundaries remain intact across multiple workers, release/reassignment, restart, and import. Resume creates no new executing interval.
8. Stale assignments retain reservations until explicit resolution. Fenced workers cannot update the record, and the dashboard states that external edits are not controlled by the service.
    After isolated replacement in workspace Y, a third plan cannot acquire unresolved old workspace X or a shared resource still held by the prior worker. A heartbeat cannot silently resurrect stale ownership.
    Device changes/path reuse cannot bypass held resources. Relayed checkpoints identify worker and relay. A stale unfenced attempt may append a recovery checkpoint without clearing holds; late fenced evidence cannot change executable state. Review/fix handoffs preserve exclusive reservations throughout.
9. The dashboard supports multiple plans/active steps, exposes workflow metadata only when supplied, shows published-state freshness, and renders untrusted titles/evidence safely. Verify representative browser behavior with synthetic data.
10. Missing Docker/service access yields an accurate unavailable report with no spawned per-task server, duplicate canonical plan, or default ASCII map. Existing bounded work and unpublished evidence are preserved.
11. Legacy graph/evidence/scope/recovery regressions still pass. Database backup/restore and schema incompatibility refusal are demonstrated in Linux containers.
     Reimporting the same source with a different key cannot duplicate its plan. Active legacy work imports held for ownership recovery, with its first-step latch preserved; changed post-handoff legacy state produces a conflict. First-store import registers its claimed execution workspace and blocks a second plan from assigning it; missing identity keeps a whole-store hold until explicit attachment.
     Restoring an older backup changes epochs, invalidates capabilities, and holds the whole store until missing post-backup work and resource use are reconciled. After global reconciliation, a claimed absent post-backup resource remains reserved across all plans until explicit stopped-use release, even when its original plan is absent. A normal restart preserves the epoch and is distinguishable from restore.
12. The container has no repository, Docker socket, or client credentials mounted, is loopback-published, and rejects missing/incorrect MCP credentials and invalid Host/Origin requests. Credentials do not appear in response URLs or logs.

These are design acceptance requirements. No runtime or implementation test has been run during this brainstorming stage.
